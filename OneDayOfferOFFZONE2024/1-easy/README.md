Открываем файл в иде, переходим на мейн. Видим функцию на ~90 строчек, судя по коду функцим и её размеру, она должна быть подъёмна для методичного ревёрсинга руками. Но давайте начнём с конца, с условия получения флага.


```c
  *(_QWORD *)flag = 0xEFBB45E15C46C3E3LL;
  *(_QWORD *)&flag[8] = 0x7CA4AE528481F490LL;
  *(_QWORD *)&flag[16] = 7837303722556665560LL;
  *(_QWORD *)&flag[24] = 0x594A28956B2B39BDLL;
  const_key[0] = 0x706050403020100LL;
  const_key[1] = 0xF0E0D0C0B0A0908LL;

    fin_decrypt((unsigned int *)&flag[8 * n], (__int64)const_key, (int)key);
  
  if ( flag[0] == 'c' || flag[1] == 't' || flag[31] == '}' || flag[7] == '{' )
    puts(flag);
  else
    printf("Hmmmm, something wrong.......... Maybe phrase is invalid?");
  return 0LL;
```

Вынесем из этого кусочка кода несколько интересных наблюдений:
- условие, которое используется для проверки флага, довольно странное (между условиями на равенство символов во флаге стоит не `&&`, а `||`), ладно может авторы опечатались (спойлер --- нет)
- единственное на что мы можем влиять для функции расшифровки `fin_decrypt()` это значение аргумента `key`, так как всё остальное устанавливается равным константе перед её вызовом. А `key` это переменная размером 4 байта. Если результат `fin_decrypt()` зависит только от её аргументов, то можно попробовать перебрать значения `key`

Посмотрим на функцию `fin_decrypt()`. Судя по декомпилированному коду как-то легко восстановить `key` на основе имеющихся данных нельзя. Но она правда не зависит от переменных кроме своих аргументов. Значит будем брутить uint32.

```c
__int64 __fastcall fin_decrypt(_QWORD *text, __int64 const_key, int key)
{
  __int64 result; 
  unsigned int i; 
  unsigned int fst; 
  unsigned int scnd;
  unsigned int round_key; 

  fst = *(_DWORD *)text;
  scnd = *((_DWORD *)text + 1);
  round_key = key << 6;
  for ( i = 0; i < 0x40; ++i )
  {
    scnd -= (((fst >> 5) ^ (16 * fst)) + fst) ^ (*(_DWORD *)(4LL * ((round_key >> 11) & 3) + const_key) + round_key);
    round_key -= key;
    fst -= (((scnd >> 5) ^ (16 * scnd)) + scnd) ^ (*(_DWORD *)(4LL * (round_key & 3) + const_key) + round_key);
  }
  *(_DWORD *)text = fst;
  result = scnd;
  *((_DWORD *)text + 1) = scnd;
  return result;
}
```



### Брутим инты

Мне пришли в голову 4 способа организовать брут:
- патчинг бинаря 
- debugger API (IdaPython, r2pipe)
- FRIDA
- самописные хуки
- *(есть ещё пятый, просто скопировать код из иды, но в моменте я не подумал об этом)*

Среди этого всего самый эффективный способ, но и требующий больше всего страданий это патчинг. При использовании r2pipe, idapy у нас будет уходить время на взаимодействие дебагера и приложения. При самописных хуках у нас совершаются длинные прыжки, что чуть тяжелее коротких. А с FRID'ой это будет как с хуками, но + накладные расходы на неё саму.

Возможно это всё экономия на спичках, но патчинг не должен быть слишком сложным, так что было выбрано максимально эффективное решение.

Что патчим:
- делаем цикл, что бы `key` принял все возможные значения
- убираем вызов `printf()` в случае фейла, просто переход на следующую итерацию цикла
- заменяем `puts(flag)` при успехе на `printf("%s: (%x)\n", flag, key);`, чтобы знать какой ключ нам дал флаг

> P.S. Патчинг вышел правильным далеко не с первого раза, так что в изменённом бинаре можно найти и другие следы патчинга кроме перечисленных.

После патчинга запускаем [получившийся бинарь](./bin-brut.out).  Он выдаёт очень много положительных срабатываний. Перенаправим его вывод в файл, в этот момент лучше иметь на диске больше 3 Гб и планы на ближайший час, два, так как примерно столько места и времени займёт полный перебор.

```bash
$ ./bin-brut.out > out.txt
```

Потом по-хорошему бы отфильтровать получившийся файл, допустим взять только достаточно длинные строки. Получившуюся выжимку можно просмотреть и руками, но давайте попробуем грепнуть "ctf", и это окажется хорошей идеей.

#### XOR2
Дальше нам встречается функции, которые работают с какой-то криптографией, по структуре и некоторым признакам шифрование напоминает [hc256](https://en.wikipedia.org/wiki/HC-256), но для нас это несильно важно. Так как единственное, что нам интересно это значения возвращаемые функцией `crypt_step()`, так как на них ещё раз ксорится наша строка. А криптография нам неважна, ведь результаты функции `crypt_step()` при каждом запуске одинаковые и не зависят от введённых данных (это можно понять с помощью динамического анализа). 

```c
int main() {
    // <...>
    init_blockgen(&crypt_obj, v16);               // hc256 vibe
    crypt_string(&crypt_obj, xored_s, 0x20u);
    // <...>
}

int64 crypt_string(crypt_t *a1, char *a2, unsigned int max)
{
  unsigned int v3; // eax
  int64 result; // rax
  unsigned int index; // [rsp+24h] [rbp-14h]
  unsigned int i; // [rsp+28h] [rbp-10h]
  unsigned int new_block; // [rsp+2Ch] [rbp-Ch]

  index = 0;
  while ( 1 )
  {
    result = index;
    if ( index >= max )
      break;
    new_block = crypt_step(a1);
    for ( i = 0; i <= 3 && index < max; ++i )
    {
      v3 = index++;
      a2[v3] ^= new_block;
      new_block >>= 8;
    }
  }
  return result;
}
```

Поставим в дебагере брейкпоинт после вызова функции `crypt_step()`, пропишем в брейкпоинте вывод регистра `rax`, будем счастливы, так как получили все нужные значения.

#### RBtree hack
> Так как мы знаем, что дерево хранит только уникальные элементы, то дальше под элементами будем подразумевать только уникальные элементы.

Так как `a1` зависит от первых 5 красных нод дерева, нужно научиться класть в дерево значения, так чтобы "контролировать" красные ноды. На самом деле это не так сложно как звучит, ведь изначально все наши значения сортируются по возрастанию и добавляются в дерево начиная с минимального.

При таком условии заметим 2 особенности:
- для одинакового числа элементов деревья будут иметь одинаковые "рисунки" (т.е. красные и чёрные ноды всегда будут на тех же местах)
![example](https://github.com/user-attachments/assets/cc61936e-5940-462b-897b-21c66edf4da0)
- зная количество элементов списка, мы можем определить цвет элемента по его месту в порядке возрастания, так как отсортированные списки тоже будут иметь одинаковый "рисунок"
![example](https://github.com/user-attachments/assets/b1cd01be-dfe8-4ef6-a0c2-5d8eb1f60688)

Тогда чтобы первые 5 красных нод имели нужные нам значения, нужно:
- определить для каждого размера дерева, номера каких элементов в отсортированном списке будут соответствовать красным нодам
- подобрать такие элементы, чтобы при их сортировке на позиции "красных нод" оказались "правильные" значения

2-й пункт оставим на будущее. Пока разберёмся с первым. Так как в нашем дереве может быть максимум 31 элемент, то все возможные деревья можно перебрать руками. Для этого воспользуемся [сайтом](https://www.cs.usfca.edu/~galles/visualization/RedBlack.html), предварительно проверив на дереве из 31 элемента, что его раскраска в нашей программе и на сайте совпадает. Найдём того 9 вариантов (различных размеров) дерева, в которых есть хотя бы 5 красных нод.

#### Возможные байты

Для начала определим, какие значения могут принимать байты перед сортировкой и добавлением в дерево, т.е. после того как наша строка дважды проксорилась.

```python
first_xor_key = b"..."
hc_xor_key = bytes.fromhex("...")
mega_key = byte_xor(first_xor_key, hc_xor_key)

possible_bytes: list[set] = []
for k in mega_key:
    psb = []
    for ch in range(0x20, 0x80):
        psb.append(ch ^ k)
    possible_bytes.append(set(psb))
```

#### Шаблон

Так как у нас есть несколько различный конфигураций дерева и значений `а1`, то будем выбирать по одной конфигурации и одному значению, и из их объединения собирать шаблон для дальнейшей генерации.

```python
# Визуализация шаблона
#  для a1 = [137, 141, 165, 175, 189] и 
#  дереву из 17 элементов со следующими
#  красными нодами [8, 10, 14, 15, 17].
# 
# Вместо * нужно подобрать числа
# так чтобы все они шли в порядке возрастания

*_*_*_*_*_*_*_137_*_141_*_*_*_165_175_*_189_*
```
> Интересный факт: так как в дерево добавляются только первые 31 элемент из 32. При генерации шаблона нужно это учитывать, и поэтому, если мы создаём шаблон для дерева на `n` элементов, шаблон будет включать в себя `n+1` элементов --- шаблон добавит 1 дополнительный элемент, который больше остальных и не будет вставлен в дерево. Без этого дополнительного элемента в дерево бы не попадал бы нужный элемент перед ним.


#### Заполнение шаблона

Так как при заполнении шаблона у нас есть ограничения на то, какие числа мы можем использовать. Напишем алгоритм, который бы это учитывал. 

Напомним, что `possible_bytes` это массив из 32 сетов, каждый сет `possible_bytes[i]` содержит внутри себя значения, которые можно получить из `i`-того байта строки. 

Идея работы алгоритма:
- выбираем из `possible_bytes` по одному сету для каждого известного числа в шаблоне, помечаем их как задействованные
- самую левую `*` в шаблоне заменяем на минимальное число удовлетворяющее условиям (что числа в шаблоне идут в возрастающем порядке и без повторений)
  - выбираем незадействованный сет из `possible_bytes` содержащий текущее число
  - если такого нет, увеличиваем текущее число на `1` и пробуем снова
  - если после этого число нарушает условия, возвращаемся к предыдущему числу, увеличивая его на `1` и повторяя все шаги заново
- после того как заполнили шаблона, пытаемся в незадействованных сетах найти числа уже имеющиеся в шаблоне (чтобы не увеличивать число уникальных элементов). Если нашли, то восстанавливаем строчку для получения флага, иначе возвращаемся на шаг назад по алгоритму

Пишем на основе этих гениальных идей [keygen](./keyGen.py). Который выдаёт нам кучу ключей.

```bash

key="+g?kETBR5>*;`@C[;{O\aEdplo%(2-K{"
```
